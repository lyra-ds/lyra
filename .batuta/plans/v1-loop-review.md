## Decisions and context

Read .batuta/specs/2026-09-12-v1-loop-review-contract.md in full. It defines mandatory preflight, evidence/exit semantics, scope exclusions, budgets, cleanup, supported environment and the difference between an audit result and a product gate. Existing .batuta/profile.md and .batuta/routing.md remain authoritative. The maintainer approved this plan and authorized proceeding with the loop on 2026-09-13. Launch remains subject to the mandatory execution preflight, with existing boundaries unchanged.

Use the existing stabilization branch, never MAIN. Sequential execution, explicit --parallel 1, pinned Node24.18.0/pnpm11.13.1, existing adapters/models only. Low is OpenCode/glm-5.3-flash, medium/high Codex/gpt-5.6-terra (high effort for high). Critical stays self and is not assigned to pending loop tasks. Escalation into self parks for the interactive conductor, never swaps routing. Each task is one verified tooling/report commit. Independent read-only review is required for high tasks. Acceptance proofs are executed by the Batuta core process outside the Codex executor sandbox, not copied from executor claims. Semantic verification is a separate OpenCode session on opencode/glm-5.3-flash via the existing low routing row, with before/after tree guard and a TASK n verdict per criterion. Require the actual journal to identify this reviewer; no executor self-attestation is acceptable. This uses the existing loop verifier, not a new routing lane or a self task. No external service, dependency, resource or release authority follows from this plan.

Before launch, the conductor must complete the execution-contract preflight, including successful global Test command in the intended execution environment and a clean dedicated branch. Do not change Test: pnpm test to a weaker smoke check. If preflight fails, stop before spending on loop tasks and propose the smallest actual prerequisite. All proposed documents must be approved and committed on the feature branch before the real dry-run; never falsify approval just to make dry-run pass.

The canonical product remains read-only throughout this review loop: packages/, public docs, manifests/locks, .github/, accepted baseline pointers and historical evidence are excluded from task write scopes. Raw review outputs may be written only to the designated fresh durable evidence root prepared by the conductor, never to old evidence paths. All code changes are review tooling. A reproduced product defect becomes a precisely scoped follow-up task; it is not silently fixed under an unrelated profile scope. The final report is required even when legitimate product failures or unavailable external gates exist. Missing execution, unsupported checks and skipped cases remain explicit non-PASS cells.
