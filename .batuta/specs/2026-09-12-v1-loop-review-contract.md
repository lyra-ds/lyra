## Minimal report and runner contract (task 1)

Use only Node built-ins and existing repository helpers. Three source files plus one small case registry are sufficient: `check.mjs`, `run.mjs`, `check.test.mjs`, `cases.json`. Do not create a general orchestration framework or duplicate Batuta, CI, existing profile machinery, compatibility fixtures or baseline collectors.

`run.mjs --case <registered-case> --audit` executes that case's real bounded producer/command(s), captures stdout/stderr and each original exit, and writes a fresh raw report below the configured durable root. It prints a compact report path/hash and explicit product verdict for the loop journal. Repeated controller proofs create new attempt directories rather than overwriting executor evidence. The registered manifest binds component/stack/engine/profile/case names and expected totals before execution. No shell interpolation of external text. Commands are argument arrays; no `|| true` or fabricated success record.

A report must include: schema/version; case ID and attempt; full source revision and product-source SHA manifest; all contributing producer/fixture hashes; exact package and lock hashes; OS/architecture/browser/tool versions; exact commands and real exits; expected and executed named cases; individual product verdicts; captured errors; negative-control provenance when applicable; precise blocker or not-applicable justification; cleanup outcomes; and paths/hashes for durable artifacts. Records cannot substitute aggregate counts for component identity. An unchanged helper omitted by an old producer's source list must be bound by this new audit manifest or explicitly tied to its exact committed source hash, not silently assumed.

A proposed result enum may distinguish `PASS`, `FAIL`, `BLOCKED` and `PENDING`. Not-applicable must cite an already approved support/release rule. Manual evidence deferred by Automated Core is a deferral, never a pass and never a reason to erase Full-profile requirements. Product support absent from a stack must not be manufactured (for example standalone Alpine CreateWorkspaceDialog or Alpine CommonJS).

**Audit exit semantics:** exit0 means the review ran or established a real environmental blocker, its report is complete and internally valid, and all findings are faithfully preserved. It does not mean every underlying test passed. Each actual failed test remains `FAIL` with its original nonzero exit. Missing/skipped/unrun cases remain non-PASS, even when the audited missing producer or unavailable platform is the finding. An unavailable environment needs an actual capability/access probe, its output and the exact unmet requirement, not a speculative sentence. Malformed/empty reports, bad hashes, wrong candidate, hidden failures, unjustified omissions, unexpected launcher failures and failed cleanup are audit-infrastructure failures: nonzero audit exit, normal loop retry/escalation. Never use this audit command as a replacement for `pnpm test`, a product test, baseline acceptance or release gating.

The corresponding strict validation mode, `check.mjs --report <path> --require-product-pass`, must exit nonzero for any required failed, blocked, pending, missing or stale cell. Task1 regression tests prove that the same honest-failure report can pass audit integrity while failing strict product qualification. Final reports must print both axes, for example `review: complete; product qualification: blocked`. No canonical release command is rewired to this tool.

Some cases are document/source audits (runtime contract, acceptance proposal, migration references, ledger draft): register exact inputs and objectively check the complete required matrix, reference existence and hashes. Independent read-only review supplies the semantic verdict; file existence alone is not acceptance. No task invents runtime thresholds or policy approval. Browser/profile tasks must execute the real profile producer; a document-only inventory cannot count as an implemented native test.

Case outputs remain durable through worktree deletion. Before task1 is accepted, its explicit `--self-test-durability` proof must use an owned temporary worktree/producer root and a short real child process, remove only that owned root, and verify the durable raw record and hash remain readable afterward. Its explicit `--self-test-verdicts` proof must run both validators against the same real captured failed child report: audit integrity succeeds, strict product qualification returns nonzero, and missing/forged reports fail both as appropriate. These executable proof commands are listed in task1 Accept, in addition to the unit suite and separate semantic review. Before final integration, the conductor checks the actual loop version's handling of gate-generated outputs: raw gate evidence must not depend on uncommitted files being swept into a commit. The final ledger/consolidation task writes tracked relative references and hashes to the durable reports already captured in the journal.
