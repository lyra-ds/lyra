# Lyra v1.0 Phase 0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete the measurable Phase 0 baseline required before the first Lyra v1.0 component-family implementation wave.

**Architecture:** Publish support policy from existing component metadata, capture bundle evidence with one reproducible packed-artifact tool, centralize dependency-decision evidence in an ADR template, and apply the approved independent-versioning transition across policy and automation. Keep baseline evidence immutable by revision; later migrations create comparison reports instead of overwriting history.

**Tech Stack:** TypeScript, React 19, MDX, Vitest, Node.js 24, pnpm 11.13.1, Playwright 1.62.1, Vite 8.2.1, Size Limit 12.1.0, Markdown, Changesets, GitHub Actions.

## Global Constraints

- The approved PRD and five foundational specifications govern every task.
- Runtime scope remains `@lyra-ds/styles`, `@lyra-ds/react`, and `@lyra-ds/alpine`; Blade is documented as an existing downstream adapter but does not block v1.0.
- Public support claims MUST come from repository-owned metadata or recorded evidence, never hand-maintained duplicate inventories.
- Automated browser policy is Playwright 1.62.1 with Chromium revision 1234 (`151.0.7922.34`), Firefox revision 1538 (`153.0`), and WebKit revision 2336 (`26.5`).
- Critical desktop workflows require Windows/NVDA plus macOS/VoiceOver records; automated results do not replace them.
- Bundle evidence MUST use packed artifacts, cold caches, production mode, fixed externals, raw/minified/Brotli bytes, Brotli quality 11, and immutable revision metadata.
- Simple primitive migrations MAY add at most `+1.5 kB` Brotli per consumer entry; complex component migrations MAY add at most `+3 kB`; larger deltas require an approved ADR.
- Styles, React, and Alpine transition to independent SemVer; affected shared-contract releases remain coordinated, unaffected packages receive no empty bump, and the v1.0 suite requires all three packages at `1.0.0`.
- No task changes production component behavior.

- [ ] **Step 3: Implement the support-row projection**

Create `apps/docs/lib/support-matrix.ts` with these public types and function:

```ts
import { components } from './components';
import { SIBLING, stackOrder, type DocStack } from './stacks';

export type SupportCell = { supported: boolean; reasonKey?: string };
export type SupportMatrixRow = {
  slug: string;
  name: string;
  stacks: Record<DocStack, SupportCell>;
};

export function getSupportMatrixRows(): SupportMatrixRow[] {
  return components.map((entry) => ({
    slug: entry.slug,
    name: entry.name,
    stacks: Object.fromEntries(
      stackOrder.map((stack) => {
        const sibling = SIBLING[stack];
        const supported =
          entry.stacks.includes(stack) || Boolean(sibling && entry.stacks.includes(sibling));
        return [stack, { supported, reasonKey: supported ? undefined : entry.absence?.[stack] }];
      }),
    ) as Record<DocStack, SupportCell>,
  }));
}
```
